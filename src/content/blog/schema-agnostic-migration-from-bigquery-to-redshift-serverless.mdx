Modern data engineering frequently demands cloud-to-cloud migrations as organizational architectures, cost models, and ecosystem strategies evolve. While managed replication platforms and Change Data Capture (CDC) pipelines dominate high-frequency migration discussions, they often introduce unnecessary operational overhead, licensing fees, and infrastructure complexity for static or discrete historical data transfers.

This technical case study details how our data platform team successfully migrated a multi-gigabyte analytical warehouse from Google BigQuery to Amazon Redshift Serverless. Faced with hundreds of tables exhibiting highly diverse, nested, and evolving schemas, we avoided the trap of manual schema definition or expensive third-party tools. Instead, we architected and executed a zero-infrastructure, fully automated **dump-and-restore** migration framework using Python, pyarrow, and the Amazon Redshift Data API.

This post details the architectural decisions, the exact code utilized, and the production-grade optimizations that enabled a seamless multi-gigabyte cutover.

## **Migration Background**

The project scenario involved a high-throughput data platform that needed to transition its data storage from Google Cloud Platform (GCP) to Amazon Web Services (AWS). Specifically, the core datasets required migration into a target Redshift Serverless workgroup environment for downstream analytical modeling.

The source dataset consisted of several gigabytes of data spread across hundreds of tables. The data profiles ranged from simple, flat relational tables to highly complex schemas featuring deeply nested structural features, token arrays, and high-precision metadata decimal fields.

## **Why We Chose Dump and Restore**

Before writing any code, we evaluated three distinct architectural patterns for the data movement phase: continuous CDC replication via managed services, an ETL-based pipeline (AWS Glue/Apache Spark), and an orchestrated **Dump and Restore** strategy.

## **Schema Discovery Strategy**

Our primary engineering challenge was the lack of detached, pre-compiled schema definition files (such as DDL scripts) from the source systems. Manually querying BigQuery information schemas for hundreds of tables and transforming them into Redshift-compatible dialects would have taken weeks and risked human error.

We addressed this by implementing **In-Storage Schema Discovery**. Since Apache Parquet is a self-describing columnar storage format, every single Parquet file contains its own comprehensive schema metadata within its file footer.

1. $1

The data was delivered into the target S3 bucket using an explicit table-to-folder convention:

`s3://s3-bucket/├── dataset_metadata_prod/│   ├── part-000.parquet│   ├── part-001.parquet│├── dynamic_token_mappings/│   └── part-000.parquet`

1. $1

The framework used boto3 to crawl the S3 bucket prefixes and identify unique table designations. Because every file within a specific table prefix shares an identical schema layout (guaranteed by BigQuery's export mechanism), the framework optimization engine only needed to pull a single sample file per folder.

To process this efficiently without filling up the host system's disk, the script writes the sample file into an ephemeral, temporary file system location using Python’s tempfile module, reads the schema using pyarrow.parquet.read_schema(), and immediately flushes the disk space once the schema data is extracted.

## **Automated Redshift Table Generation**

Once the framework isolated a sample Parquet file's metadata, it passed the fields into a custom translation matrix. This translation matrix automatically mapped the physical and logical pyarrow datatypes to the appropriate Amazon Redshift relational datatypes.

1. $1

The framework applied the following standard type conversion matrix:

1. $1

BigQuery environments frequently utilize STRUCT and REPEATED fields to handle nested JSON data or hierarchical business schemas. In legacy data warehouse migrations, converting these structures required data engineers to either completely flatten the data into wide tables or break them out into separate, complex child tables with foreign key relations.

Amazon Redshift’s native SUPER datatype solves this problem completely. The SUPER datatype stores schemaless or semi-structured data up to 16 MB per row in a highly optimized, internal binary format. By mapping Parquet list and struct elements directly to SUPER, we preserved the exact nested topology of the source BigQuery data. This meant downstream analytics engineers could query nested arrays using standard, intuitive dot-notation and unnesting syntax without changing their underlying data models.

## **Detailed Code Deep-Dive**

1. $1

The execute_sql function abstracts away the execution of commands against Amazon Redshift Serverless. Instead of establishing a long-running, stateful database connection pool that is prone to network drops, it submits an asynchronous statement request via redshift_data.execute_statement().

The Redshift cluster immediately responds with a unique execution tracker (Id). The code then enters a structured while-loop that queries the status of this ID every 2 seconds via describe_statement(). If the state transitions to FAILED or ABORTED, the script raises an exception containing the explicit database error payload, allowing for rapid debugging.

1. $1

The arrow_to_redshift function maps pyarrow schemas to their corresponding Amazon Redshift SQL datatypes. It handles fixed-width types (int32, int64, float64) and addresses specific database constraints like maximum column size limitations:

`elif pa.types.is_string(dtype):    return "VARCHAR(65535)"`

Additionally, it dynamically handles variable fixed-point numeric scales:

`elif pa.types.is_decimal(dtype):    return f"DECIMAL(&#123;min(dtype.precision,38)&#125;,&#123;dtype.scale&#125;)"`

This protects Redshift from processing errors by limiting the decimal precision to its maximum supported length of 38 digits.

1. $1

The migrate_table core function cleans up column names by removing stray quotation marks to prevent DDL syntax errors. After building the column mapping string, it drops any pre-existing table variations to guarantee a clean target environment before executing the CREATE TABLE script.

Directly following successful table creation, the framework triggers a high-speed, parallelized data ingestion using Redshift's native COPY command. By pointing the COPY statement to the table's S3 folder prefix (s3://&#123;BUCKET&#125;/&#123;table_prefix&#125;), Redshift reads all underlying Parquet file chunks in parallel, distributing the loading workload evenly across all available compute nodes.

## **Technical Highlights: Why This Architecture Works**

This migration framework stands apart from traditional data movement methods because of several key architectural choices:

1. $1

S3 acts as a highly resilient, infinite buffer that decouples GCP extraction routines from AWS ingestion loops. If an ingestion task fails due to a schema constraint violation, the source files remain safely intact on S3. This eliminates the need to run expensive, concurrent extraction processes on the source systems again.

1. $1

Traditional migration worker nodes must establish and preserve continuous stateful JDBC/ODBC network paths. Any network blip or timeout across hours of loading can break the processing thread.

The **Amazon Redshift Data API** removes this infrastructure liability. It functions entirely as a secure, stateless HTTP endpoint. Long-running SQL operations are submitted asynchronously, returning a tracking identifier immediately. The Python controller simply polls the Data API for execution completion status, making the framework resilient to local worker process restarts.
